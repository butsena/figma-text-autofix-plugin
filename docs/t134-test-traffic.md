# T-134: отделять проверку плагина от обычной работы

Проект решения на приёмку, 29.10.2026. Основа — main `ca337779a3b55c08d1a91b315cbecdd8d547e0e0`, принятый аудит T-130 (F04/L01), результаты T-135/T-144 и чтение рабочих формул 29.10.2026. Эта задача выбирает способ; код, рабочий приёмник, события и формулы не изменены. Внедрение требует отдельной задачи после принятия решения.

## Решение для продукта

У каждого нового отправленного события явно указывать назначение запуска: **обычная работа** или **проверка**. Версия отвечает только на вопрос «какая сборка», а не «зачем её запустили». Локальная разработка по умолчанию ничего не отправляет. Проверки сохраняются для диагностики, но не увеличивают использование, исправления, часы, рубли и даты начала рабочего учёта.

Для неизвестного происхождения оставить отдельное состояние **режим не указан**. Не угадывать его по человеку, файлу, времени, суффиксу версии или случайному ID сессии. Это режим запуска, а не доказательство происхождения запроса или реальности пользовательской работы: публичный приёмник не аутентифицирует отправителя.

## Что обнаружено сейчас

1. `package.json`, `vite.config.ts`, `src/config/analytics-config.ts`: обычный build/dev выключает отправку, `build:release` включает её через `ANALYTICS=1`. Отдельной команды QA и независимого поля режима нет. В исходном конфиге по-прежнему версия `0.18.0`.
2. `scripts/analytics-apps-script.js`: `validateEnvelope_` пересобирает envelope без поля режима. Произвольное новое поле старый приёмник отбросит. `smokeAppend()` непосредственно пишет версию `0.18.0`, поэтому не является безопасной проверкой рабочих итогов.
3. Рабочие «Результаты», «Источники орфографии» и «Сбои и восстановления» исключают `LOWER(TRIM(plugin_version))="smoke"`; dashboard использует свои COUNTIFS с исключением `smoke`. Semver с суффиксом `-qa` или `-smoke` этим условием не исключается. Сверять нужно все источники, а не только видимые итоговые числа.
4. `Методика!B35` ищет первый `spellcheck_requested` без исключения smoke. Это отдельный пробел покрытия: тестовая строка способна задать дату начала учёта, даже если рабочий счётчик её исключает. Значение и формула сейчас не исправлялись.
5. T-135/T-144 проверялись отдельными сборками с явным историческим значением версии `smoke`; их строки остаются в events и исключены из основных рабочих сводок. Это действующий обходной процесс, а не уже внедрённое независимое разделение режимов.
6. История без явного режима не доказывает обычное использование. В частности, аудит T-130 не установил происхождение четырёх запросов 22.10.2026 без smoke. Не переименовывать и не удалять их задним числом.

## Выбор способа

| Способ | Преимущества | Ограничения | Решение |
| --- | --- | --- | --- |
| Отдельный endpoint и отдельная таблица для проверок | Тесты физически не попадают в рабочий журнал | Нужно поддерживать две конфигурации/развёртывания; тестовая копия может отличаться от рабочего приёмника; ошибочный URL всё ещё возможен | Не выбирать сейчас: лишнее сопровождение при нынешнем объёме |
| Явный режим, один приёмник, отдельная колонка журнала и единое правило отчёта | Одни правила валидации; проверка того же приёмника; настоящая версия сохраняется; тесты доступны для диагностики | Требуется согласованно обновить клиент, приёмник, повторы и все формулы | **Рекомендуется** |
| Сохранить только `plugin_version=smoke` | Уже работает для вручную подготовленных smoke-сборок | Теряется настоящая версия; легко забыть подмену; обычная тестовая версия загрязняет итоги | Только временный порядок до внедрения |

Отдельная таблица пригодится позднее, если изменятся требования к доступу, нагрузке или хранению. Сейчас подтверждённых оснований для неё нет. Явный режим не добавляет персональных или текстовых данных.

## Сценарии

| Что делает человек | Отправка | Режим | Где виден результат |
| --- | --- | --- | --- |
| Разрабатывает или локально проверяет исправления | Выключена по умолчанию | Не отправляется | Локальный результат/автотесты |
| Проверяет, что события доходят из Figma | Включена отдельной QA-командой | Проверка | Сырой журнал и диагностическая выборка; рабочих итогов не меняет |
| Проверяет приёмник синтетическими запросами | Только по разрешению на конкретный живой прогон | Проверка | Тот же диагностический поток; часы/рубли не начисляются |
| Работает опубликованным плагином | Включена релизной сборкой | Обычная работа | Рабочие показатели с прежними ограничениями полноты доставки |
| Проверяет будущий выпуск перед публикацией | Сам релизный файл — локально с перехватом отправки; живой прогон — отдельной QA-сборкой из того же кода | Проверка для живого прогона | Без подмены реально отправленной рабочей записи тестовой задним числом |
| Запускает старую опубликованную версию | Прежнее поведение | Режим не указан | Совместимая история, явно не подтверждённый обычный поток |

В самом плагине не добавлять пользователю переключатель аналитики «тест/работа». Режим задаётся процессом подготовки сборки. Если релизную production-сборку действительно использовать для живого теста, она отправит production; приёмник не умеет определить намерение человека. Поэтому такой тест не обещаем автоматически исключить.

## Требования к отдельной реализации

### Контракт и хранение

- Необязательное для совместимости поле envelope `traffic_mode`: только `production` или `test`. Новый клиент всегда отправляет одно из них. Отсутствие у старого клиента — `unknown` при хранении, не production. Явные null, пустая строка, неверный тип или значение отклоняются целиком до записи.
- Добавить к events восьмую колонку H `traffic_mode`, не сдвигая A:G, не пересоздавая лист и не переписывая прежние строки. Перед внедрением проверить занятость H, сохранить backup и заголовки. Старые пустые H означают неизвестный режим; отсутствие режима у нового legacy-запроса сохранять как `unknown`.
- Историческое точное значение `plugin_version=smoke` продолжает исключаться из рабочих показателей. `smoke` с новым `traffic_mode=production` — противоречие, отклонить; с `test` — допустимо. Суффиксы semver не определяют режим: `1.2.3-qa` без поля остаётся unknown, а с `production` считается заявленным production. От ошибочного выбора защищает сборка, не догадки приёмника.
- Не добавлять тексты, имена, URL макетов, ID Figma или постоянные ID людей. Существующие закрытые payload, семь событий, таймаут и отсутствие очереди сохраняются.
- Для повторной доставки с `event_id` сравнивать также нормализованный режим: тот же ID/содержимое/режим — duplicate; другой режим — conflict, не новая рабочая строка. Отсутствие и `unknown` для legacy сравнивать согласованно. Не менять ранее принятую область защиты T-135 и не обещать дедупликацию всех семи событий.
- Передачу нового поля можно оформить совместимым расширением schema v1 с едиными клиентскими/серверными проверками. Старый collector поле молча отбросит: подтверждённая новая capability в GET обязательна перед выпуском нового клиента. Должна отражать именно режимы, а не один только номер deployment.

### Сборки и проверка выпуска

- `dev`/`build`: нет отправки. Один `ANALYTICS=1` без явно выбранного режима больше не должен давать молчаливый production; завершать сборку ошибкой, если отправка включена без режима.
- `build:qa`: отправка включена, `traffic_mode=test`, настоящий номер и метаданные сборки, отдельные имя/папка для Figma. Не редактировать общий исходный конфиг на время сборки и затем возвращать его вручную.
- `build:release`: отправка включена, `traffic_mode=production`, явная валидная версия выпуска. Запретить специальную версию `smoke` и случайное QA-переопределение режима. Связать событие с версией, которую действительно собирают, а не со старым `0.18.0` в исходнике.
- Сохранять для обоих файлов commit, SHA-256, версию, режим и адрес приёмника. Проверять значения из готового файла, не только из команды или исходного конфига. Нельзя доказывать идентичность QA/release-бандлов: конфигурация различается. Код должен происходить из одного принятого commit.
- Релизный файл проверить локально с перехватом fetch: он формирует production и правильную версию, но запрос не уходит. QA-файл проверить в Figma с test. Это проверяет разные границы; не выдавать QA-прогон за живой production-прогон того же файла.
- `smokeAppend()` убрать из нормального порядка проверки или переделать на явный test с теми же правилами приёма. Не использовать прежнюю запись `0.18.0`. В deployment не запускать onceSetup/setupDashboard для существующей книги.

### Рабочий отчёт и история

Единая классификация (в этой очередности):

1. `traffic_mode=test` либо старый точный smoke-маркер — **проверка**.
2. `traffic_mode=production` и не smoke — **обычная работа, явно помеченная**.
3. Пустой режим либо `unknown`, не smoke — **режим не указан**.
4. Невозможные/неверные сохранённые значения — **ошибка данных**: не включать молча в рабочую аналитику; вывести диагностический контроль. Приёмник такие новые строки отклоняет.

Сохранить прежний смешанный накопительный итог: явная обычная работа плюс не исключённая неизвестная история, с заметной оговоркой. Не называть весь этот итог достоверно очищенным от тестов. Отдельно показывать количество записей без режима и часть данных с явным production. Не исключать молча всю старую историю — это необоснованно обнулит известную активность.

Применить одно правило включения ко всем исходным диапазонам: «Результаты», dashboard, «Методика» (включая B35), источники 10 графиков, «Источники орфографии», «Сбои и восстановления», даты первого полученного рабочего события и все 41 UTC-периода. Не расширять задачу до редизайна. Часы/рубли/коэффициенты не менять; тестовые события не создают рабочую дату покрытия.

Граница появления явного рабочего режима — первая полученная **production**-запись, а не дата PR, внедрения приёмника или тестового прогона. Это начало наблюдаемого покрытия, не доказательство, что все клиенты перешли. Старые клиенты могут присылать unknown и после этой даты. Историю и даты не восстанавливать по догадке.

## Контрольные примеры для будущей реализации

| Версия | Поле | Приём | Класс отчёта |
| --- | --- | --- | --- |
| `1.2.3` | production | Да | Явная обычная работа |
| `1.2.3` | test | Да | Проверка, рабочие значения и даты неизменны |
| `1.2.3` | Нет | Да, unknown | Режим не указан, не подтверждённый production |
| `1.2.3-qa` | Нет | Да, unknown | Режим не указан; суффикс не доказательство |
| `1.2.3-qa` | test | Да | Проверка |
| `1.2.3` | null / пусто / иной тип / опечатка | Нет | Нет новой строки |
| `smoke` | Нет | Да, совместимость | Проверка по старому явному маркеру |
| `smoke` | test | Да | Проверка |
| `smoke` | production | Нет | Нет новой строки |
| Любая допустимая | Тот же event_id, другой режим | Conflict | Нет второй строки |

Проверить все семь событий, прежние T-135 source/replay и T-144 failed/recovered/legacy, отсутствие приватных данных, ошибку сети и обычное исправление. Одно включение `ANALYTICS=1` без режима должно провалить сборку. Сборка с QA-конфигурацией должна провалить проверку выпуска.

На копии отчёта: production + test + unknown + старый smoke; test не меняет ни показатели, ни даты; unknown остаётся неизвестным; прежние исторические итоги сохранены. Контроль по каждому периоду: валидные записи = production + test + unknown; не сравнивать число записей с суммой исправлений. Сверить 10 графиков и 41 период. Контрольные строки после проверки удалить из копии; рабочие строки не трогать.

На рабочем приёмнике после отдельного разрешения — только test-пробы, сохранённые для диагностики; сравнить формулы и рабочие итоги до/после. Способность принять production проверить на изолированном хранилище, не создавая синтетическую production-строку в рабочей книге. Переход endpoint, новый доступ или отдельная инфраструктура не нужны.

## Порядок внедрения и выпуск до него

1. Принять T-134 и создать отдельную задачу реализации: клиент/сборки, приёмник/H, единое правило отчёта, совместимость и проверки выпуска. Ориентир **4–7 часов чистого времени**, включая ручные проверки и перенос; не прибавлять повторно к уже существующей оценке эпика без пересчёта состава. T-131 закрывает только оставшуюся общую согласованность, не повторяет эту миграцию.
2. Подготовить и проверить код и копию отчёта; согласовать рабочее обновление. Сначала приёмник с capability, затем правила отчёта, затем QA и только затем новый Community-клиент. Если после обновления приёмника ещё нет отчётного фильтра, не отправлять test с обычной версией: он попадёт в прежние итоги.
3. Проверить новый процесс, принять реализацию, отдельно разрешить merge/публикацию. Условие остановки: нет capability/фильтра/верного режима в готовом файле — новый поток не выпускать.
4. Возврат: заранее сохранить текущие рабочие формулы и код приёмника. При откате клиента оставить совместимый новый приёмник и фильтры, чтобы уже записанные test не попали в итоги. Не откатывать старые формулы поверх нового потока без приостановки отправки и безопасной работы с новыми test-строками. Историю не удалять как способ исправить отчёт.

До внедрения T-134 не блокирует публикацию принятого функционального кода: остаётся нынешний процесс. Локальные проверки без отправки; живые аналитические проверки — только отдельной сборкой с точным `plugin_version=smoke`; выпуск — отдельным релизным файлом с настоящей версией. Не публиковать QA-манифест. Проверку production-конфигурации выполнять с перехватом сети. Нельзя обещать, что обычная версия, использованная для теста с отправкой, автоматически исключится.

## Связи, результат и ограничения

- T-130 F04/L01 — основания и неизвестная история, не переписываются.
- Принятые T-135/T-144 — сохраняются payload, source, исходы сбоев и смысл реальных повторных действий; тестовый режим не делает дубль отдельным успехом.
- T-131 — использовать это решение при согласовании подписей/покрытия; не дублировать внедрение фильтров. T-124/T-127 могут использовать классы потоков, не считать unknown реальными людьми/макетами.
- Человек может ошибиться с файлом, а публичный endpoint принимает заявленный режим: абсолютная гарантия чистоты и полная доставка не обещаются. Релизные проверки снижают риск, а не определяют намерение любого пользователя.
- Это проект, не принятый продуктовый выбор и не реализация. Новая задача пока не создана; задача T-134 остаётся In progress до приёмки Антоном. Никакие новые события в рабочую книгу в ходе T-134 не отправлялись.
