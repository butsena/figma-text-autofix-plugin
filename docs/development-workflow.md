## 3. Роли и ручной контроль

- **Антон / ответственный человек** определяет постановку и приоритет, согласует ready, проверяет результат, принимает ручной QA, решает вопрос merge и подтверждает Done. Конкретный ответственный за приёмку должен быть указан до передачи результата.
- **Cursor** остаётся текущим исполнителем кодовых задач с исполнителем `cursor`. Получает явное поручение либо согласованную задачу `automation_state=ready`, выполняет реализацию, проверки, QA-обновления и создаёт PR в разрешённом репозитории.
- **Codex** помогает изучать код, уточнять постановки и процесс, готовить документы и проводить ревью. Доступ к GitHub или таблице не заменяет назначение исполнителя и не разрешает забирать задачи Cursor. Передача конкретной реализации Codex возможна только по явному решению человека с фиксацией области поручения; массовой смены исполнителя нет.
- **Будущий Automation Engine** выполняет только принятые правила запуска и записи технических состояний. Он не принимает собственную работу, не ставит ручной `passed`, не выдаёт разрешение ready и не выполняет самостоятельный merge/Done.

Явное поручение человека разрешает названный объём. Оно не включает запуск соседних задач, всей очереди, расписания, выпуск новой версии в Community или изменение общего исполнителя. Для очереди до ready нужны разрешённый репозиторий, выполненные зависимости и полная постановка. Задачи Done и архивные не выбираются даже при оставшемся `automation_state=draft/ready`.

### Текущий процесс: отдельное явное поручение

Пока очередь не внедрена, работа возможна по отдельному поручению человека. Исполнитель перечитывает актуальную постановку и правила, сверяет зависимости, подтверждает названный человеком репозиторий и ограничивает работу порученной областью. Если Registry ещё не реализован, явно названный репозиторий фиксируется в результате полной ссылкой; пустой repository ID не заполняется выдуманным значением и не считается готовностью к будущей очереди.

Изменения готовятся в отдельной ветке/checkout, выполняются доступные обязательные проверки и QA-обновления, возвращается конкретный результат с SHA и ссылками. Результат кодовой доработки — отдельный PR с проверками; он не разрешает merge. Поля трекера обновляются в пределах согласованной работы с перечитыванием результата. Назначенный исполнитель остальных задач остаётся прежним.

Ручная проверка, решение о merge и Done остаются человеку. Наличие готовых документов, отдельной реализации или прямого поручения не означает внедрение Engine, защищённого взятия либо расписания. Разделы ниже задают требования к будущему автоматизированному циклу; их нельзя представлять как уже работающий механизм.

## 4. Два независимых состояния и свидетельства

**Продуктовый «Статус»** описывает положение задачи в трекере. **`automation_state`** описывает этап конкретного автоматизированного выполнения. Одно поле не вычисляется слепо из другого. Значения продуктового статуса используются по действующей схеме трекера; этот документ не добавляет новые.

Разрешённые технические значения: `draft`, `ready`, `working`, `failed`, `cancelled`, `pr_created`, `ready_for_qa`, `changes_requested`, `approved`, `merged`. Не записывать сюда старые YAML-значения `in_progress`, `review`, `done`.

Предлагаемые переходы для кодовой задачи:

| Состояние / переход | Кто разрешает или фиксирует | Обязательное свидетельство |
| --- | --- | --- |
| `draft` | Человек либо агент при подготовке постановки | Задача ещё не разрешена к запуску. Пустые обязательные поля перечислены явно. |
| `draft → ready` | Человек | Принятая постановка и критерии, исполнитель, разрешённый repository ID, выполненные зависимости, границы изменений и способ проверки. |
| `ready → working` | Исполнитель / Engine после проверки и защищённого взятия | Run ID, версия входной постановки, исходный commit, владелец запуска; отсутствие другого активного выполнения. |
| `working → pr_created` | Исполнитель после создания PR | Ссылка на отдельный PR, head SHA, результаты обязательных проверок; успешное создание подтверждено чтением GitHub. |
| `pr_created → ready_for_qa` | Исполнитель | Завершены автоматические проверки и QA-обновления; есть инструкция ручной проверки, ограничения и список QA add/change/retest. |
| `ready_for_qa → changes_requested` | Человек | Конкретные замечания, ожидаемый результат и связь с QA/PR. Не создаётся новая несвязанная реализация той же задачи. |
| `changes_requested → working` | Исполнитель в пределах согласованных замечаний | Та же задача и связанный PR; новая попытка связана с прежним Run ID. Существенное расширение постановки требует решения человека. |
| `ready_for_qa → approved` | Человек | Явная приёмка с head SHA, принятыми критериями и сохранённым ручным результатом. Одного отсутствия замечаний недостаточно. |
| `approved → merged` | Факт фиксирует агент / Engine после решения и действия человека | GitHub подтверждает merge этого PR; записаны merge commit и дата. Сам переход не вызывает merge и не ставит продуктовый Done. |
| Активная попытка → `failed` | Исполнитель / Engine | Где остановилась работа, причина, сохранённые артефакты, что осталось непроверенным, условие безопасного повтора. |
| Активная попытка → `cancelled` | По решению человека | Причина и граница остановки; изменения и PR сохранены, продолжающегося исполнителя нет. |

Путь `pr_created → ready_for_qa` может быть зафиксирован одним результатом, если все свидетельства уже доступны. Нельзя объявлять готовым PR с упавшими обязательными проверками. Перечень проверок берётся из реального проекта: у плагина есть `npm run test` и `npm run build`; не писать «lint/typecheck пройдены», если такие команды не определены и не запускались.

Любой новый commit после `approved` делает прежнюю приёмку неактуальной для новой версии. Работа возвращается в `working` либо `ready_for_qa` по факту готовности; затронутые ручные сценарии получают `needs_retest` с сохранением истории. Приёмка другого SHA не переносится молча.

### Merge, приёмка и Done

1. PR создан — изменение доступно для рассмотрения.
2. Ручная приёмка — человек принял конкретную версию и критерии.
3. Merge — GitHub подтвердил попадание PR в целевую ветку по решению человека.
4. Smoke-check целевой ветки — релевантная проверка принятого результата после merge.
5. Done — человек подтвердил выполнение постановки с учётом приёмки, merge и smoke-check, если задача включала кодовый PR.

Результат smoke-check указывает, кто и что действительно проверил. Автоматический тест не заменяет проверку в Figma. Если merge произошёл вне штатного пути или после него найден дефект, агент сообщает расхождение; не выдумывает прежнюю приёмку и не переоткрывает Done автоматически.

### Завершённые задачи без кодового PR

Ручная задача, проверка доступа, миграция данных или принятый документ могут быть завершены человеком без PR. Для такого результата достаточно соответствующих постановке свидетельств и человеческой приёмки; `merged` к нему неприменим. Для новых ручных задач техническое поле оставляется пустым, если действующая схема допускает пустое значение. Если схема требует значение, способ представления согласуется отдельно; не добавлять новый enum и не ставить фиктивный `merged`.

Исторические сочетания вроде Done + `draft` не являются разрешением запуска. Их нормализация — отдельная согласованная миграция по фактам, а не автоматическое массовое исправление. Для T-046 факт PR merge есть; для остальных задач он должен быть проверен отдельно. Принятый Done не снимается из-за неполного исторического технического поля.

## 5. QA и передача результата

После любой правки поведения действует [.cursor/rules/qa-checklist-on-logic-change.mdc](../.cursor/rules/qa-checklist-on-logic-change.mdc): обновить определения, результаты агента при необходимости и переносимый Canvas; затронутые ручные результаты пометить `needs_retest`, сохранив историю. Чистое документальное изменение без смены поведения не требует нового сценария плагина.

До `ready_for_qa` результат содержит:

- T-ID, repository ID, ветку, PR и точный head SHA;
- краткое описание поведения и покрытия критериев;
- фактически выполненные проверки с результатами и ограничениями;
- QA add/change/retest и путь к сохранённым артефактам;
- шаги ручной проверки и то, что ещё требует решения человека.

Ручные `passed`, `failed`, `not_run`, `needs_retest`, `processed_legacy` отделены от агентских `ok`, `ok-code`, `fixed`, `partial`. Агент может сохранить переданный человеком результат с указанием источника, но не объявляет собственную автопроверку ручным `passed`.

Экспорт с `unsavedSession: true` остаётся несохранённой сессией до записи файла. Проверка переносимости должна проходить через реальный Canvas Export/Import, а не только сериализацию модели JSON. Импорт и последующий экспорт должны сохранять различие ручных статусов, даты, проверенный commit, историю, комментарии и вложения. До подтверждения этого свойства ограничения описываются явно; полная сохранность не заявляется.

Кнопка «В бэклог» создаёт чат с инструкцией записи в таблицу через авторизованный Sheets MCP. После проверки дублей замечание связывается с исходной задачей/PR; самостоятельный новый дефект получает новую draft-задачу. Комментарии и вложения не очищаются после передачи, запись перечитывается и подтверждается T-ID. Старые backlog Canvas и `backlog.yaml` не обновляются.

## 6. Порядок подготовки и запуска

Это карта зависимостей процесса, а не перечень новых задач. Актуальные постановки и решения ready остаются в таблице. Используются существующие T-ID без дублей.

| Этап | Существующие задачи и результат | Что должно быть готово до следующего этапа |
| --- | --- | --- |
| 1. Принять контракт | T-047 — правила выбора, переходов, прав и остановки | Человек принял правила; неизвестные поля и противоречия названы. Проверка прав создания PR отделена от разрешения очереди. |
| 2. Привязать проект и проверить вход | T-030 — исполнители и Repository Registry; затем T-031 — проверка готовности | Реальный разрешённый репозиторий, полная постановка, проверенные зависимости и понятный отказ для неполной задачи. |
| 3. Подготовить исполнение и защиту | T-032 — адаптер запуска/наблюдения; T-033 — Run ID, защита от двойного запуска, ошибки, cancel/retry | До первого запуска задач через Engine действуют защищённое взятие и безопасный повтор. Реализация адаптера сама по себе не разрешает запуск очереди. |
| 4. Довести доставку результата и приёмку | T-034 — отдельная ветка, проверки, PR; T-035 — ручной QA, возврат, разрешение merge и smoke-check | Связи задача ↔ запуск ↔ PR ↔ SHA ↔ QA сохранены; возвращённая задача не создаёт второй PR; merge/Done остаются под контролем человека. |
| 5. Провести ограниченный пилот | T-048 после T-047, готового QA-процесса и необходимых T-030–T-035 | Подготовлены 2–3 небольшие независимые задачи; человек согласовал ready. За первый прогон последовательно выполняются максимум две. Результаты и сбои разобраны, ручная приёмка и закрытие подтверждены человеком. |
| 6. Включить регулярный запуск | T-049 только после принятого результата T-048 | Явно выбраны среда, расписание/событие, лимит, восстановление, остановка и уведомления. Отдельно разрешено включение регулярного запуска. |

T-046 не заменяет T-035: хранение QA-данных и управление человеческой приёмкой — разные части процесса. Исправление обнаруженного ограничения QA оформляется без автоматического снятия Done с T-046 и должно быть проверено до пилота в той части, на которую пилот опирается.

Принятие правил T-047 предшествует реализации зависимых механизмов, но не доказывает их работу. Если в критериях T-047 требуется практически подтвердить защиту от повторного взятия или создание PR, эта часть подтверждается результатами T-033/T-034. До такого свидетельства нельзя отмечать её выполненной только по наличию документа. Человек должен согласовать границу: T-047 как принятый контракт с проверкой через зависимые задачи либо сохранение финальной приёмки T-047 до получения этих результатов. Это не повод запускать очередь до защиты.

Репозиторий реализации каждой T-030–T-035 нельзя выводить из того, что этот документ лежит в репозитории плагина. Привязка определяется постановкой и Registry: задачи standalone-трекера не переносятся в код плагина по умолчанию.

## 7. Ошибки, владение запуском и повтор

Предлагаемый контракт Engine:

1. До изменений перечитать задачу, зависимости и разрешённый репозиторий. Проверить, что задачу не изменили после разрешения ready. Изменение существенных входных данных требует повторной проверки готовности.
2. Получить защищённое владение задачей и сохранить Run ID вместе с версией постановки. Обычные Sheets read → write → read не являются атомарной блокировкой. До реализации в T-033 механизма, исключающего одновременное взятие, параллельный запуск одной очереди запрещён.
3. Повторный вызов с тем же идентификатором выполнения возвращает существующее состояние, ветку и PR. После сбоя сначала найти существующие артефакты и проверить, остановился ли прежний исполнитель; новый PR вслепую не создавать.
4. При недоступной постановке, противоречии требований, неизвестном репозитории, невыполненной зависимости или провале обязательных проверок остановить зависимую работу и сохранить понятную причину. Непроверенную задачу не объявлять готовой.
5. При ошибке записи результата сохранить Run ID, SHA, PR и неприменённое обновление как диагностический артефакт. Не создавать рабочую копию бэклога и не продолжать выбор новых задач. После восстановления доступа перечитать строку и разрешить конфликт, затем записать результат без потери человеческих правок.
6. `failed → working` допускается после устранения указанной причины и явного решения о повторе; перед продолжением снова проверяются входные данные и владение. `cancelled` автоматически не возобновляется.
7. После запроса отмены не брать следующую задачу. Отмена фиксируется как завершённая только после подтверждения остановки исполнителя; сделанные изменения, ветка, PR и журнал не удаляются.

Run ID, версия постановки, владелец, время и граница попытки — логические требования. Их точное хранение и атомарность определяются в T-032/T-033; документ не утверждает наличие соответствующих колонок или API в текущем трекере.

## 8. Свидетельства пилота и регулярный режим

T-048 должен подтвердить реальный цикл без YAML-копии: выбор → защищённое взятие → реализация → тесты/сборка → QA → PR → ручной возврат либо приёмка → merge → smoke-check → человеческий Done. Отдельно проверяются повторный вызов без второго запуска/PR, ошибка записи результата, провал проверки и изменение строки человеком. Имитация этих ситуаций не выдаётся за проверку механизма, которого ещё нет.

До T-049 человек принимает журнал пилота и оставшиеся ограничения. Затем отдельно выбираются исполнительная среда и способ запуска. GitHub Actions не являются обязательным выбором только из-за размещения кода на GitHub; ручной запуск, планировщик и CI имеют разные роли.

Регулярный режим имеет лимит задач за запуск, ограничение времени, проверяемую остановку, восстановление и защиту от повторов. Уведомления отправляются о готовом результате, сбое или необходимом решении человека; неизменившееся состояние не создаёт регулярный шум. Права ready, ручной приёмки, merge и Done не расширяются при включении расписания.

## 9. Решения, которые ещё нужны

- Принять в T-047 точную семантику `approved` и ручных переходов из раздела 4; выбрать ответственного за приёмку каждой задачи. Предложение: `approved` означает принятую человеком версию head SHA.
- Подтвердить repository ID и репозитории реализации задач трекера; разрешение на репозиторий плагина не распространяется автоматически на другой проект.
- В T-032/T-033 выбрать место хранения запусков и механизм атомарного владения. До этого нельзя обещать защиту от конкурирующих запусков или безопасное расписание.
- Уточнить границу приёмки T-047: правила нужны до T-030–T-035, а практические свидетельства защиты и доставки PR появляются в зависимых реализациях. Не объявлять их уже проверенными и не создавать циклическую зависимость «T-047 Done до реализации собственных доказательств».
- Для исторических Done-задач отдельно согласовать необходимость нормализации `automation_state`; не подставлять `merged` задачам без PR. Это не блокирует документирование фактов и не требует массовой миграции прямо сейчас.
- Перед T-048 подтвердить конкретные тестовые задачи и разрешить ограниченный пилот; перед T-049 выбрать среду/триггер и отдельно разрешить регулярный запуск.
